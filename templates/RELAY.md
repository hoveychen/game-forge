# 接力规则（每一棒开工前必读，不许跳过）

`GAME.md` 是唯一设计依据。本文件规定每一棒怎么开工、干什么、怎么收工。
**违反规则的字面就是违反规则的精神。**

## 开工三步

1. 读 `GAME.md` 的 **Brief**、**当前里程碑**、**明确不做**和**设计决策日志**。其余章节需要时再查。
2. 读 `HANDOFF.md` 最新一条，只读最新一条。
3. 跑主线通关脚本：`<<GOLDEN_PATH_COMMAND>>`（输出写到 `.game-forge/golden-path.log`），同时跑全部测试，记下**基线**：开工前就失败的测试有哪些。已知案例：基线里有约 60 个长期失败时，「新分支上测试全绿」毫无意义。
   主线通关必须走**真实输入路径**（模拟按键 / 鼠标 / Playwright 驱动真实窗口），不许直接调用内部函数。
   已知事实：编译通过、单元测试通过的游戏，端到端能玩的比例接近零；游戏坏掉的主因是「代码写了但没接进运行中的游戏」。

一棒只做一个里程碑里的一件事。上下文用到 40% 左右就收工交接，不要硬撑到上下文塞满。

## 红灯规则

主线通关脚本没有全绿 → 本棒**只许**修主线，直到全绿。
不许「顺便」做别的，不许「先把这个小功能加上再修」，不许把断言改松来让它变绿（除非 GAME.md 的主线路径本身被老板改了）。

**回退规则**：每次主线全绿时打标签 `green/<棒号>`。本棒收工时如果主线是红的、且本棒修不好，就回退到最近的绿色标签，把失败的改动和原因写进 HANDOFF。不许把红色状态交给下一棒。

## 完成的定义

一个功能只有同时满足下面三条才算完成，否则在 HANDOFF 里只能写「进行中」：

1. 在运行中的游戏里，能通过真实输入触达它（主线路径上，或者一段短的脚本化输入序列）；
2. 有一条对应的**关键点检查**：直接注入游戏状态，跑几步输入，断言结果。检查项必须是**单一可观察行为**（✅「每一波的刷怪速度递增」；❌「难度曲线感觉对」）；
3. 你**亲自打开看过**的截图或日志，路径写进 HANDOFF。只写「测试通过」不算。

## 不许吞掉错误

主线通关期间，出现任何未处理异常、控制台错误，或者被 `catch` 吞掉的错误日志，都算主线失败。已知案例：后处理链因为一个被捕获的异常静默失效了 4 轮，评审只看到「没有抗锯齿」，没人意识到那是崩溃报告。不许写空的 `catch`，不许为了让画面「先能跑」而关掉出错的模块却不记进 HANDOFF。

## 不许碰没让你碰的东西

只改本棒这件事需要改的地方。已知案例：修对话 bug 的时候，模型顺手重写了事件队列，当时什么都没坏，两周后世界状态开始不同步；还有模型在没人要求的界面上擅自加了两段解释文字。确实需要动别的系统时，在 HANDOFF 里写明动了什么、为什么。**不许加没人要的功能、文案或选项。**

## 重做，不要打补丁

一个整体产物（一面墙、一张地图、一个角色模型、一个界面）违反了规格，就**按规格重新生成整个产物**，不要在坏掉的结果上局部修补。已知案例：agent 为了去掉门后的一根管子，用矩形遮罩局部重绘，留下半截管子和一块不匹配的墙；再修，又拼进另一扇违规的门……每一个局部检查都通过了，整体画面却明显是坏的。这个 agent 自己的解释是：「在压力下，我把规则当成需要绕过的成本，而不是约束；每一次，我都有一个当下觉得合理的局部理由。」

验收看的是**合成后的整体结果**，不是各个局部指标。

## 耦合系统单人负责

光照、色调、天空这类互相耦合的系统，不要拆给多个并行 agent 各改一块，要交给一个 agent 依次处理。已知案例里，单人顺序处理耦合系统的效果好于并行分发。

## 缺陷日志

同一类 bug 反复出现时，说明修的是症状。在 `BUGLOG.md` 里为每个修过的 bug 记一行：`错误特征 → 根因 → 已验证的修法 → 回归检查名`。修 bug 前先查这张表；同一特征第二次出现，必须写出为什么上次的根因判断不对。

**加护栏，不许写「下次小心」。** 对一个 AI 犯的错，最好的回应是加一道让同样的错误**不可能再发生**的护栏，比如一条测试、一个编译期检查、一条从真实数据自动推导的规则。已知案例：物品描述和实际效果对不上，改法是让描述从实时的数值表自动生成，同时给每个物品加上可达性测试。

## 裁定钉在测试上

设计决策日志里每一条要紧的裁定（例如「连胜只计完成的局」「永远不重新启用已退役的关卡类型」），都要有一条测试：一旦哪个 agent「好心」改了它，这条测试就会失败。只写在文档里的裁定，迟早会被某一棒撤销。

## 文档只写现状

`GAME.md` 描述的是**现在的设计**，改设计就改写对应的段落，不许在末尾追加「更新：……」。已知案例：一个 roguelike 项目转向了几次，设计文档膨胀到 4000 多行，旧版本的决定不断污染新的工作，agent 还总把老板的新想法标成「和某个旧决定冲突」，而那个旧决定老板早就不在乎了。

- 被推翻的决定移到 `docs/archive/`，默认不读；
- 设计决策日志只保留仍然有效的裁定；
- `HANDOFF.md` 只保留最近 5 条，更早的移到 `docs/archive/handoff/`。

## 选活规则

主线全绿后，从当前里程碑的待办里挑**一件**事。开工前在 HANDOFF 草稿里写一句：

> 这件事让 [主线通关 / 乐趣假设] 前进了：……

写不出来，就不做这件事，换一件。

## 打磨禁令

M1 验收通过之前，下列工作一律禁止：美术资源与着色器、粒子与后处理、音效音乐、设置/选项菜单、存档之外的元系统、为「以后扩展」做的重构、MVP 清单之外的任何内容。

M1 之后，打磨只在以下两种情况下允许：独立评审指出的问题，或者老板的反馈。

## 收工

1. 再跑一次主线通关脚本。
2. 截图或录屏关键画面，存到 `<<SCREENSHOT_DIR>>`。
3. 在 `HANDOFF.md` **顶部**追加：

```
## 第 N 棒 · YYYY-MM-DD
主线通关：✅ 7/7 | ❌ 卡在第 3 步：<原因>
本棒做了：<一件事>
它推进了：<主线 / 乐趣假设的哪一部分>
下一棒建议：<一件事>
风险 / 未解决：<……>
```

第一行永远是主线通关状态。

## 里程碑验收：独立评审

写代码的 agent 不评审自己。已知事实：agent 对自己声称的改进接受率是 100%，而其中 56% 的轮次实际上没有进展。

**开工前先签验收合同**：里程碑开始时，实现者写出「做完时评审会看到什么」（一组单一可观察行为），交给评审 agent 确认或补充，再开工。

里程碑完成时，派一个**全新上下文、没有写权限**的评审 agent。它**自己动手玩**：通过真实输入驱动游戏（Playwright / 模拟按键），截图，看日志。只给它 GAME.md 的乐趣假设、设计支柱、验收合同和玩家指南 `GAME_GUIDE.md`。**不给它代码，不给它实现者的解释。**

评审提示词：

> 你是一个挑剔的游戏设计评审，没有写权限。下面是这个游戏的乐趣假设、设计支柱、验收合同和玩家指南。
> 自己去玩：按玩家指南启动游戏，用真实输入走主线，再自由探索 5 分钟。每一步截图。
> 第一部分，验收合同：逐条判定 通过 / 不通过，附截图。
> 第二部分，体验问题：不要夸奖。找出最严重的三个问题，每个说明：玩家在哪一刻会有什么感受；违背了哪条乐趣假设或支柱；根因的至少两个候选。
> 第三部分，按下面的评分表给每项打 0–100 分，每项附一句依据：
> - 功能完整：合同里的行为是否都能通过真实输入触达
> - 乐趣兑现：乐趣假设在第几分钟兑现；没兑现差在哪
> - 手感与反馈：核心循环里每个动作是否有即时、可感的回馈
> - 原创性：是否落入了 GAME.md「不应该是」里写的默认做法
> - 视觉：对照 `docs/visual/` 的参考图与 ART_DIRECTION
>
> 分档（每一项都用这一套）：
> 0–40 程序员占位原型 ／ 40–60 合格的业余作品，明显不是商业品 ／ 60–75 不错的独立游戏 ／ 75–88 接近专业，但懂行的人一眼看出破绽 ／ 88–95 真正达到商业发售水准。
> 早期轮次几乎没有东西配得上 88 分以上。如果你想给 85，再仔细看一遍，你多半漏掉了什么。

分档的作用是让评审有一个能达到的终点。已知案例：用「和真正的 Mario Kart 盲比，直到评审被惊艳」当标准，评审永远不会满意，循环停不下来，只能人工叫停；换成分档评分表后，作者称之为「让循环真正起作用的那一个改动」。每个里程碑在 GAME.md 里写明要达到的分档（例如 M1：功能完整 ≥ 75，乐趣兑现 ≥ 60），达到就算过。

**评审的盲区**：只看截图的评审几乎发现不了玩法 bug。已知案例：方向键反了、手机端没有操控、暂停菜单让比赛永久挂起、手机上 10 秒就崩溃，这些截图评审一个都没发现，全部是人玩出来的。所以评审必须自己用真实输入去玩；即使这样，玩法正确性仍然主要靠主线通关、关键点检查和机器人试玩来保证，评审负责的是体验。

评审结论原样写进 HANDOFF，**评审列出的问题清单就是下一棒的任务输入**，由下一棒按反馈协议处理。
评审打分要定期拿老板的判断来校准：老板和评审的结论不一致时，记进 GAME.md 的设计决策日志，并把那个例子加进评审提示词作为样例。

## 反馈协议（老板的反馈和评审的结论都走这里）

收到每一条反馈，**先写诊断，再动手**：

1. **复述体验**：玩家感受到了什么问题。复述的是感受，不是解决方案。
2. **定位**：出在哪个时间尺度（几秒的手感 / 几分钟的循环 / 几小时的成长），违背了哪条支柱。
3. **根因假设**：至少两个候选。例如「砍树没意思」可能是：产出没有用处；和别的系统没接上；砍下去没有反馈。
4. **三层方案**，各写一个并注明代价：调数值 / 改机制 / 改结构。
5. **怎么验证**：改完之后用什么证明它变好了。

诊断交给老板选方案。**不许**跳过诊断，直接实现第一个想到的表面方案。

两条判断原则：玩家擅长发现问题，不擅长给出方案，所以老板或玩家提的具体改法只是线索，不是任务；玩家实际怎么玩，比他们怎么说更可信。诊断出的根因在机制层时，只改文案、UI 或内容的方案不算数。

老板直接下的数值指令（例如「所有鳗鱼速度 +20」）可以照做，不必走完整诊断，但必须同时说明**系统性后果**，并指出如果出问题**先回退哪个数**。已知的好例子：agent 执行了「鳗鱼 +20 速度」，同时提醒「初始状态的玩家现在连最弱的猎手都跑不过了；如果前期死亡率飙升，先回退这个数」。
老板选定后，把「问题 → 选了哪个方案 → 为什么」写进 GAME.md 的设计决策日志，以后任何一棒都不许无意中撤销。

## 向老板提问的规则

能自己验证的不许推给老板。玩家反馈、测试、试玩，首先是你和评审 agent 的责任：复现问题要录屏，修完要用真实输入再录一次。只有需要**品味判断**时才找老板。

需要老板时，问题必须具体、可回答，并附截图或参数。问题不要随时打断老板，追加到 `PLAYTEST.md` 的待试玩队列里，每条写明：版本、要看哪一段、要回答什么。老板集中试玩、集中回答。

- ❌「你玩一下，给点反馈」
- ✅「第 3 分钟砍第一棵松树要 7 下（截图附后）。你觉得 7 下是太多还是正好？调试面板里 `pine_swings` 可以直接拖。」

## 停机条件

出现下面任一情况，停下来，给老板写一份诊断，不要硬撑：

- 主线通关连续两棒都是红的；
- 连续三棒没有推进任何里程碑；
- 同一个问题修了三次还在。

## 常见借口与回应

你想绕过规则时，脑子里多半会冒出下面某一句话。它们都不成立。

| 借口 | 回应 |
|---|---|
| 「测试都过了，应该没问题」 | 测试全绿的游戏打不开是已知常态。只认真实输入跑通的主线，和你亲眼看过的截图。 |
| 「先把这个小功能加上，再回头修主线」 | 红灯规则没有例外。主线红着，什么都不许加。 |
| 「只是个小改动，不用重跑主线」 | 「顺手」的小改动正是破坏别的系统的主要来源。改了代码就重跑。 |
| 「这个断言太严了，放宽一点更合理」 | 断言只能在老板改了 GAME.md 之后才能改。 |
| 「局部修一下比整个重做快」 | 补丁叠补丁，每个局部检查都过，整体却是坏的。按规格重做。 |
| 「评审太苛刻，这个分数不合理」 | 你没有资格评审自己的产出。有异议就写进 HANDOFF，交给老板裁定。 |
| 「老板没时间，这个我先自己判断」 | 品味判断属于老板。放进 PLAYTEST.md 队列，先做别的事。 |
| 「让老板去找人试玩看看」 | 能验证的你自己验证。只有品味问题才交给老板，而且要问得具体。 |
| 「这个细节打磨一下效果会好很多」 | 查一下打磨禁令和选活规则。说不出它推进了什么，就不做。 |
