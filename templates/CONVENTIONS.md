技术与开发约定：
- 引擎：Godot 最新版 + GDScript。引擎自带的能力（物理、动画树、IK、粒子、全局光照、导航）直接用；Godot Asset Library 和 GitHub 上成熟的插件，以及 CC0 或允许商用的模型、骨架、动作、材质、音效，优先拿来用。只有找不到合适的现成品、或现成品做不到下面 GDD 要的效果时才自己写。用到的第三方资源在 CREDITS.md 记下来源和许可。
- 资产走离线管线：源文件放 assets/src（像素图、参数文件、下载来的原始模型），导入工具（EditorScript 或命令行脚本）把它们烘焙成 .glb / .tres / 贴图放进 assets/build，游戏运行时只加载烘焙产物，不在运行时生成模型。SDF、体素化、程序化建模都可以用，但只用在导入工具里；运行时 shader 里的光线步进只留给云、液体、雾、特效这类本来就要实时算的东西。外来资产也过这条管线，统一比例、材质和配色，让它们属于同一个世界。
- 工具和算力先行：开工头一件事是把迭代工具备齐——能单独启动某个资产或某个镜头并截图的实验场景、出资产接触表的验收台（见下面「资产验收台」）、只重烘改动资产的增量烘焙（按源文件和参数的哈希缓存）、每个资产带耗时的烘焙日志、长任务放后台作业不干等；GDD 有节奏曲线的目标数值表时，再加一个能无头快进跑完一局的节奏 bot，按那张表的口径输出指标，调数值时拿它和 sim/ 里的纸面曲线对照。导入工具本身也要按性能写：SDF 求值、体素化、AO、光照烘焙这类逐点计算不要用 GDScript 循环，用 compute shader（RenderingDevice；Godot 加 --headless 时拿不到它，要开一个小窗口跑）或 GDExtension / 现成原生库，同一个场只算一次。目标是单个资产几秒内重烘、全量一两分钟内跑完。这台机器上同时跑着别的会话，CPU 常年是满的，别指望靠多开线程救慢算法；跑完的进程收掉，不留孤儿进程。算力是预算：烘一轮要等好几分钟，就只能少试几轮、调低精度凑合，本来能做得更精细的效果就做不成了。
- 美术设计先于开发：动手写代码前，按下面 GDD 的视觉方向和美术路线，用生图工具（Fleet 里是 fleet__image / fleet__image_edit）做概念设计——2–3 张关键游戏画面（按 GDD 的镜头角度）、一张调色板、主角与主要角色/敌人的设定图、核心道具和建筑的设定图，全部用最终画风（体素就画成体素渲染，低多边形就画成低多边形），存进 concept/。之后造资产、调光照、做打磨都对着这些图来，定期把游戏截图和它们并排看，差在哪里就改哪里。像素图、贴图这类源文件可以直接从设定图出发放进 assets/src。
- 表面细节交给生图工具：形体用几何、SDF 或现成模型造；屏幕、海报、招牌、布料花纹、木纹、地表、污渍这类表面信息，用生图工具以 concept/ 的图为风格参考出图，做成平面卡片图集、可平铺材质（加推出的法线）和贴花，经导入管线上到模型上（没有 UV 的用三平面投影）。不要靠顶点色和手工几何雕细节，那样永远是干净的色块，到不了概念图的信息密度。
- 位图资产都交给生图工具：UI 图标、物品和技能图标、角色头像、角色脸上的五官和每个表情的贴图、按钮和面板底图、天空盒和远景、粒子贴图（烟、火花、光斑、碎屑）、加载图和过场插画，同样以 concept/ 的图为风格参考出图，再经导入管线切图、抠透明、缩放、打图集。五官和表情以设定图里的表情表为参考出正面图，投影到脸部 UV 上，表情靠换贴图切换。不要用代码拼 SVG 路径、用 PIL 之类的绘图库按坐标画形状、或写 shader 现算来代替这些图——几何函数画出来的图标、五官和程序化天空，信息密度和概念图差一截。只有本来就该实时变化的部分（昼夜过渡、云的流动、数值进度条）才用 shader 或代码画，叠在生图的底子上。
- 资产对照设定图逐轮收敛：角色、主要敌人、核心建筑这类主角级资产，动手造之前先对着 concept/ 里的设定图写一份参考分析，存成 concept/notes/<资产名>.md——剪影和几大体块、比例（写数字：头身比、肩宽/头宽、长宽高比）、设定图的机位和焦距感、各部分材质和粗糙度、5–8 个色值、非有不可的特征。然后先在实验场景里摆出和设定图一致的机位，机位不对，后面怎么比都是错的。造型按「剪影体块 → 次级结构 → 表面细节」三个阶段走，每个阶段结束在这个机位截图，和设定图拼成左右对照图看，写一份按影响从大到小排的差距清单，先修最大的几条再截图；比例和剪影没对上之前不要加细节。每个阶段最多改三轮，三轮后还差得远，说明这条做法到不了，换路线（换现成模型、换生图卡片、改形体方案），不要继续微调参数。对照图和差距清单留在 concept/compare/，阶段收没收尾看对照图，不看感觉。
- 资产验收台：和实验场景同一天建一个验收台场景，只放待验资产，光照和机位全部固定，前后几轮的截图才能直接比。光照至少五套：一个中性 HDRI 环境、正午硬光、黄昏低角度暖光、夜间单盏点光、强逆光；GDD 里游戏自己有的光照环境（昼夜、室内外、地牢）也各做成一套预设。台边放灰球、镜面球、色卡和一个标准身高的参照人，地面铺 1 米网格，比例和材质亮度都对着它们看。每个资产入库前跑一个脚本自动出一张接触表：8 个方向（每 45° 一张，再加俯视）× 每套光照的转台截图，按游戏实际镜头的角度和焦距在近、中、远三个距离各截一张（远处看剪影和可读性，也顺带看 LOD）；角色和带动作的道具，再把每个动画片段按固定间隔抽帧拼成一行，看穿模、滑步、关节翻折和片段之间的过渡；2D 素材换成在几种游戏背景色上、按游戏里的实际像素尺寸各摆一张。接触表存成 review/<资产名>.png，资产改动后重跑覆盖。入库和阶段收尾都看这张表，不要只看设定图机位那一张：对照收敛管的是像不像设定图，验收台管的是换个角度、换个光、动起来、拉远了还成不成立，有一格不成立就修到成立再入库。
- 开发顺序：先备齐上面的迭代工具，再打通管线——挑一类核心资产，从源文件一路走到游戏里看见，直接用最终画风；再让核心玩法循环能玩；然后铺 GDD 里的内容量；最后做视觉清单的打磨。
- 性能：Apple Silicon Mac 上 1080p 稳定 60fps；出网页或手机包时，目标是发布的最弱设备（中端手机）上也稳定 60fps，开发机的帧率代表不了手机（手机每像素的着色能力只有开发机的几十分之一）。下面几件事要在写第一个着色器、打第一盏灯之前定下来，等内容铺满再改就要动整个项目。画质分档只用一个入口来判断，按设备类别分（手机上的浏览器也要认出来），分辨率、MSAA、阴影、密度、人数上限都读这一个档位。不随时间变的东西不要在着色器里每像素现算（多八度噪声、维诺纹理、程序花纹），离线烘成可平铺的贴图，运行时取一次样。不要靠成堆的实时灯，多盏小灯烘成光照贴图、光池或体素。像素数的乘数要封顶：网页包不要让设备像素比超过 1.75，渲染比例和 MSAA 跟着画质档走，MSAA 解析只解颜色，不要连深度一起解。主线程不要同步等 GPU：运行时不读回网格、贴图、帧缓冲，需要的数据在生成时自己留一份。着色器变体在加载页编完：每种材质和灯光组合各画一帧；开关灯用改强度，不用增删或隐藏灯。大量同类对象（人群、头顶名牌、骨骼姿势）由一个管理器按 10–20 Hz 统一更新，屏外的停掉，不要每个对象各挂一个每帧回调，也不要每帧改材质参数。全屏不透明界面打开时停画 3D。一次性的重活（加载脚本、解码图片、排版）放到加载页或分帧做，不放在玩家第一次点按钮的那一帧。音频不依赖主线程准时：总线和效果在配置里静态声明，不在运行时增删，网页用平台原生播放。性能工具和迭代工具同一天建：游戏里带一个性能面板（网页用 ?perf=1 打开），显示设备像素比、帧时中位数和 p60（帧时不超过 16.7 ms 的帧占的比例）、draw call、图元、着色器现编次数，带一排拿掉某一大块的开关（藏人、藏建筑、藏界面、关 MSAA、关阴影、降渲染比例），再加一个在固定场景下轮流量这些开关的自动对照；另外备一个能在 release 包里按函数排热点的 profiler。每加完一大块内容就开面板看，掉帧时先用开关或 profiler 找出最贵的那一块再改，不要靠墙钟和猜。减三角、减重叠绘制这类改动在手机上常常不省，贵的是每像素的着色运算、寄存器和带宽。Godot 里的对应做法：网页上的手机靠 web_android / web_ios 特性识别；MSAA 只解颜色要在导出后改 index.js 里 blitFramebuffer 的掩码；关灯把能量设成 0；总线写进 default_bus_layout.tres；profiler 用带 Tracy 的 release 导出模板。
