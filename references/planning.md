# 规划阶段（A0–A8）

## 总原则：你出草稿，老板给品味

人很难凭空说清自己想要什么，但看到具体草稿时，能立刻说出「不对，不是这个」。所以：

- **一次只问一个问题**，而且先给出你的草稿或猜测，再问。
- **禁止问泛问题。** 下面这些问题只会换来泛回答，是平均化的源头，不许问：
  「目标用户是谁」「核心玩法是什么」「你想要什么风格」「有什么具体需求」「希望有哪些功能」。
  改成：给出 2–3 个具体选项让老板挑，或者给出一份草稿让老板否决。
- **老板的品味是标准答案，不是噪声。** 老板否决的东西，记进 GAME.md 的「明确不要」，之后任何一棒都不许偷偷加回来。
- **规模默认往小压。** 「地理上小，系统上密」。老板想法越大，越要主动砍，并解释砍掉的东西在 MVP 之后怎么长回来。

## A0 定档：这是什么品类，乐趣在哪个时间尺度

读老板的想法，对照 `genre-lenses.md` 判断品类，然后用一句话告诉老板：
「这类游戏的乐趣主要在 [几秒 / 几分钟 / 几小时] 这个尺度上，所以规格的细节会重点投在 [……]。」
混合品类就分别说明主次。老板不同意就以老板为准。

## A1 幻想与乐趣假设

依次拿到三样东西（每次一个问题，先给猜测）：

1. **情感幻想**：玩家是谁，为什么在这里，想逃离或追求什么。（Open Blue：社畜崩溃，「I'm done」。）
2. **参考作品**：每部**分别**借什么、**拒绝**什么。只说「像 Stardew」不算，要说「借 Stardew 的季节节奏，拒绝它点一下就完成的耕地」。
   参考作品必须是模型熟悉的名作。已知案例：参照 Call of Duty、Mario Kart、Rocket League、Zork 的都成了，参照训练数据里很少的 Pitfall 就失败了。参考作品冷门时，要把它的机制完整写出来，不能只报名字。
   拿到参考作品后，**你要主动联网考据**：键位、关键数值、机制细节、界面流程，写进 GAME.md 对应的系统卡。已知现象：「一句话做出惊艳游戏」的案例几乎都是复刻名作，因为原作本身就是一份完整规格，agent 可以查。原创游戏没有这份免费规格，只能靠考据参考作品的具体做法来补。
3. **前十分钟**：希望玩家经历什么，在哪里可以自由偏离。

老板说不清的时候，有两个办法能帮他说出来：

- **倒推法**：假装游戏已经上线，写出商店页的一段简介和三条玩家评测（一条五星、一条三星、一条差评），让老板改。老板改动的地方，就是他真正在意的东西。
- **约束驱动**：不要让 AI「发明一个游戏」，而是问一个具体的问题：「[某个约束或主题] 怎样才能支撑一个不只是 [某参考作品] 换皮的机制？」已知案例：一款在 16 天内上架 Steam 的游戏，就是从「钉子和弹珠怎样支撑一个不是 Peggle 复制品的机制」这个问题开始的。

然后写出**乐趣假设**，格式固定：

> 当玩家 [具体动作 / 情境] 时，会因为 [原因] 感到 [具体情绪]。MVP 的任务是在第 N 分钟内把玩家送到这个时刻。

乐趣假设写不具体（例如「玩家会觉得很爽」）就不许往下走。

同时指出**这个游戏「住在」哪个循环里**：玩家重复最多、手感决定一切的那个几秒到几十秒的循环。已知案例：一个卡丁车游戏做了 4 天、127 个 agent，最有价值的反馈来自一个路人：「卡丁车游戏的全部都在漂移接加速这个循环里。先做手感，赛道以后再加。」这个循环的手感要在 M1 之前调好，优先级高于任何内容扩充。

「好玩」本身没法评判，所以要从 MDA 框架的八种体验里选出 1–2 种作为主目标，并写进乐趣假设：感官（Sensation）、幻想（Fantasy）、叙事（Narrative）、挑战（Challenge）、社交（Fellowship）、发现（Discovery）、表达（Expression）、消遣（Submission）。之后每个系统都要能说出它服务于哪一种体验。Open Blue 的主目标是幻想（逃离都市）和表达（选择过哪种生活），次目标是消遣。

## A2 三个方向草稿

基于 A1 写三个**真正不同**的方向（在某个关键轴上分叉，而不是同一个东西换皮）。每个 150–250 字，包含：幻想、开局的第一个有分量的选择、核心循环、哇时刻、明确不做的东西。

老板挑、混搭或全部否决。全否决就问**一个**问题找出偏差在哪，再出三个。直到老板说「就是这个感觉」。

## A3 系统展开

对每个系统写一张卡（agent 起草，老板审）：

每个数值都要标出处：`[考据: 来源]`（从参考作品或资料查到）、`[老板定]`、`[暂定]`（等调试面板调出来）。**不许编造数值却不打标记**，否则后续 agent 会把拍脑袋的数字当成设计意图来守。

```
系统名：
玩家动作：          （玩家具体按什么、做什么）
即时反馈：          （这一下的手感：动画、音效、数字、镜头）
产出：
产出去向：          （被哪些系统消耗 / 卖掉 / 解锁什么——不许为空）
成长阶梯：          （1–N 级各解锁什么，写具体名字）
校准锚点：          （至少一个带数字的例子，如「松树：3 级 7 下，5 级 5 下」）
这个系统不应该是：  （一句反默认的约束，如「钓鱼不是点水→等→出鱼」）
设计理由：          （为什么这样设计，让后续 agent 在未写明处做出一致决定）
```

**校准锚点**是给 AI 的样板：只要给几个例子，它就能推出风格一致的其余数值，不需要穷举。**「不应该是」**把 AI 从最平均的默认做法里拉出来，每个系统至少一条。

## A4 内容样本（内容驱动型游戏必做，其他品类做哇时刻那一段）

乐趣如果来自内容（谜题、剧情、台词、关卡、角色），内容就是设计本身，必须在规划阶段真正做出来，不能留到编码时再生成：

- 解谜：前 5 个谜题完整设计，包括每个谜题的「原来如此」是什么。
- 叙事：第一场戏完整写出。
- 关卡驱动：第一关的完整布局与节奏。
- **Best-of-N：每一块关键内容至少出 10 个候选，由老板挑。** 单次生成是平均水平，从 10 个里挑出来的就不是。
- **用具体的随机种子代替「要有创意」。** 已知案例：一个自动游戏工厂发现，叫模型「更有创意」没有用；有用的是从 195 个具体主题（潮间带、电报机、酸面团发酵……）里每批随机抽 5 个发给它。准备一个具体的种子池，每次生成候选时抽几个。
- **能机器证明的内容质量，就让机器证明。** 解谜类用求解器证明每一关都有解，而且解是唯一的，并算出最少步数；证明不了的关卡不上线。知识类内容要联网核实。已知案例的规矩是：「没有证明，就没有声明」。
- **内容驱动型游戏的已知陷阱**：AI 生成的内容默认偏浅。已知案例：一款因果推理小游戏上了 HN 首页，玩家的批评集中在内容上，比如错误选项一眼就能排除、「这是历史测验，不是谜题」。AI 模拟的玩家只发现了界面问题，没有发现内容无聊。内容好不好，只能靠老板和真人来判断。
- 内容存成数据文件（json/yaml/md），不写死在代码里，方便后续替换。

## A5 闭环检查（机械执行，不靠感觉）

1. **资源流表**：列出每种资源、物品、货币的来源和去向。任何一行的去向为空 = 断头资源 = 不通过。
2. **系统四件套**：每个系统都要有 行为 → 反馈/经验 → 解锁 → 产出的用途。缺一件就不通过。
3. **第一天逐分钟模拟**：用文字模拟玩家前 15–20 分钟（或一整个游戏日），每一分钟写玩家在做什么、看到什么、为什么想做下一件事。标出乐趣假设的时刻落在第几分钟。出现「玩家不知道该干什么」或「这一步没有理由去做」的地方就是断点。
4. **隐性需求清单**：这些要求老板通常不会说，但决定了游戏能不能玩。每一条都要明确写进 GAME.md，并落成断言：
   - **终止性**：每一局、每一关都一定能结束吗？（真实案例：弹药打光后比赛永远结束不了。）
   - **可解性**：每个关卡、谜题都一定有解吗？（真实案例：先模拟出一个可执行的解，再反推关卡布局。）
   - **对手真的会行动**：AI 敌人会进攻、会追击吗？（真实案例：规格只写了「AI 对手」，结果人机从不进攻。）
   - **成长与难度的相对速度**：玩家战力如果是复利增长，敌人血量线性增长，后期几秒就被秒掉。写出两条曲线，对比一下。
   - **经济闭环**：钱会不会越滚越多失去意义，或者卡死没法继续？
   - **平台与视口**：在哪些设备、分辨率、输入方式下必须能玩？
   - **胜利条件真的生效**：达成目标后游戏真的会结束吗？（真实案例：迷你高尔夫进洞之后什么都没发生，玩家又把球打出了洞。）
   - **可读性**：玩家能一眼分清单位和地面、敌人和背景吗？（真实案例：一款 RTS 的单位和地上的落叶分不清，玩家说「这根本没法玩」。）
   - **操控方向**：按左键角色真的往屏幕左边走吗？左右相对镜头反向是几乎每个项目都会犯的 bug，而输入探测只能证明「按键改变了状态」，证明不了方向对不对。要从按键到旋转、再到屏幕上的方向，把正负号追一遍。
5. **前 5 分钟决策清单**：列出玩家在前 5 分钟里做的每一个决策。每个决策检查两件事：有没有一个永远正确的选项（有的话就不是真正的决策）；选了之后，后面的状态会不会不同（不会的话就不重要）。内容驱动型游戏尤其要做这一步。

任何一项不通过就回 A3 改，不许带着断头进入实现。

## A6 MVP 切割

写三样东西：

- **做**：具体清单（Open Blue 的写法：3 块地、9 个技能各 1–5 级、25–40 个配方……）。
- **明确不做**：同样具体。这张单子和「做」一样重要，它防止之后某一棒顺手加功能。
- **MVP 要回答的一个问题**：例如「在这个小体素世界里生活好不好玩？」
- **不变式**：运行时永远不许出现的失败，写成可检查的规则。例如「行人绝不能在玩家视野内凭空消失」「任何时候按 Esc 都能回到游戏」「一局比赛一定会结束」。规格要写清**做什么**和**不许发生什么**；**怎么做**（架构、渲染管线）可以放权给 agent。

数量用「恰好 N 个」来写，而不是「几个」「一些」：「恰好一个模式、恰好 8 种道具」「一张打磨到位的地图加一把出色的武器，胜过又宽又浅的内容」。

然后定义**主线通关路径**：一串步骤，每步带可以机器检查的断言。例如：

```
1. 新游戏开局 → 断言：角色在出生点，库存为空，金钱 = 5000
2. 走到树枝处拾取 3 根 → 断言：库存 branch >= 3，木工经验 > 0
3. 生火 → 断言：场景中存在 campfire 实体，燃烧中
……
7. 卖鱼买种子并种下 → 断言：地块状态 = planted
```

主线通关必须通过真实输入驱动。每一个断言都必须是**单一可观察行为**（✅「库存 branch >= 3」；❌「砍树感觉顺畅」）。

另外，为每个系统准备几条**关键点检查**：直接注入一个游戏状态（例如「角色站在松树旁，木工 3 级」），跑一小段输入，断言结果（「7 下之后得到 pine_log」）。已知数据：这类从规格推导、用状态注入执行的检查，和人工判断的一致率约 92%；让 agent 自由探索着玩来判断，只有约 59%，而且慢 16 倍。主线通关管「接没接上」，关键点检查管「每个系统对不对」。

机器人要断言**效果**，不能只断言**活动**。已知案例：机器人每秒下达 39 条指令，却一发都没打出去，测试照样通过。要断言的是「敌人血量下降了」「库存里多了木头」，而不是「发出了攻击指令」。

**断言全绿不等于能玩。** 真实案例：52 条断言全部通过，机器人试玩 6 局全部开局暴毙；测试报告全绿，打开游戏却是黑屏。所以还要一个**机器人试玩**：按人类的输入频率和反应速度玩完整一局（或一个游戏日），统计能活多久、能走多远、卡在哪。每修一个 bug，就补一条对应的断言。

**agent 试玩要有边界。** 它能证明一个机制确实改变了状态，但证明不了手感：实时操控、时机、响应速度，它观察不到。每个机制确认一两次就停，不要反复试玩去追手感。手感问题写进 `PLAYTEST.md`，留给老板。

## A7 实现层

1. **技术栈**：语言、渲染方案、平台、性能目标（帧率、最远缩放下的帧率）。
2. **可测性是第一天的架构需求**，不是之后补的：
   - 可设种子的随机数，固定时间步长；
   - 无头模式可以快进模拟；
   - 状态查询接口。web 游戏沿用 OpenAI `develop-web-game` skill 的约定：`window.render_game_to_text()` 返回当前状态的文字描述，`window.advanceTime(ms)` 按固定步长推进。自动玩家和评审都通过这两个接口「看见」游戏；
   - 游戏核心和渲染分离：核心逻辑无渲染依赖、固定 tick、随机数可设种子，用测试来强制保证。这是自动试玩可靠的前提；
   - 状态注入接口：从一份快照直接加载到任意游戏状态（关键点检查要用）；
   - 脚本化输入，走真实输入路径（自动玩家用它来走主线）；
   - 截图 / 录屏命令（评审 agent 要看）。
   - 玩家指南 `GAME_GUIDE.md`：怎么启动、操作方式、目标、胜负条件。评审 agent 靠它来玩，不许看代码。
3. **视觉规格用图和具体数值，不用形容词。** 美术风格、UI、镜头构图用文字传达会严重失真。规划阶段就产出：
   - 参考图：参考游戏截图、生图工具画的情绪板和关键画面、UI 的 HTML 原型，存进 `docs/visual/`；
   - `ART_DIRECTION.md`（美术圣经）：调色板色值、太阳角度、材质规范、角色比例、镜头参数。已知案例：一份写到太阳角度和色值的美术圣经，是 11 个并行 agent 能做出统一画面的原因。
   - **绕开 AI 的美术弱项。** 人类角色和人脸是一贯的短板。选择能藏住这一点的美术方向：体素、低多边形、剪影、长袍兜帽、非人角色。Open Blue 选体素，不管是有意还是无意，都绕开了这一点。
   评审 agent 拿游戏截图对照这些图和 ART_DIRECTION 打分。
4. **单一数据源。** 地图、可行走区域、物品表、配方表这类数据只在一处定义，渲染、碰撞、逻辑都从这一处读。真实案例：「可行走区域」在多处各自维护，模型临时手工修补，越修越乱。
5. **手感参数全部做成调试面板里可以实时调的滑杆**（移速、手感、数值），调好的值写回 GAME.md。手感没法提前规定，只能调出来。已知案例：一款赢得 AI 游戏 Jam 的弹球游戏，作者专门做了游戏内的台面编辑器，拖动摆放、调每个零件，git 历史里满是「peg bounce 1.49 → 1.491」这样的提交。物理常数这类东西 AI 调不好，需要人坐在那里一遍遍弹球。
   摆放类的东西（HUD 位置、物件布局）也做成游戏内编辑器，让老板自己拖，不要让老板用文字描述「往左一点」。
6. **游戏内报 bug 热键。** 老板试玩时按一个键（例如 F8），游戏自动把一条记录追加到 `PLAYTEST.md`：当前状态快照、截图、位置、老板输入的一句话。快照能直接喂给状态注入接口来复现，反馈协议从这里开始。
7. **界面功能先出原型，不写代码。** 已知案例的经验：大功能的第一版几乎从来不对。先让 agent 出 HTML 原型或静态稿，老板确认之后再实现。
8. **里程碑**，每个都带验收标准：
   - **M0 行走骨架**：灰盒 + 占位图形，主线通关脚本全绿。零美术。先做「玩具」：核心动作本身不挂任何目标，玩起来也有意思吗？重主题包装救不了糟糕的设计。
   - **M1 乐趣假设首次可体验**：玩家在预定的第 N 分钟内到达哇时刻；独立评审通过；老板回答一个具体问题。
   - **M2 起**：按 MVP 清单铺开，每个里程碑都要保持主线全绿。

   每个里程碑的验收分三层：客观（脚本/断言/帧率）、独立评审 agent、老板的一个具体问题。

## A8 落盘

GAME.md 最顶部**原样保留老板最初的那段话**，一字不改。后续每一棒都能回头对照：现在做的东西还是不是老板当初要的。

在项目仓库根目录写入：`GAME.md`（按模板填满）、`RELAY.md`（从模板复制，替换命令占位符）、空的 `HANDOFF.md` 和 `BUGLOG.md`、`GAME_GUIDE.md`、`CLAUDE.md` 片段、主线通关脚本的桩（此时是红的，这正是 M0 的目标）。

再写一份一页纸的 **Brief**（约 30 行），放在 GAME.md 的原话之后。格式参照 WorldBuild Bench 的任务书（`sources/reddit-hn/worldbuild-bench-pinned-briefs.md`）：名称、设定、美术方向、手感、核心循环、目标（带数字）、必需机制、胜负条件、操控，最后一句「概念是锁定的——把它执行好，不要替换它」。每一棒开工时先读 Brief，需要细节时再查 GAME.md 的对应章节，而不是每次都把整份 GAME.md 读进上下文。

**用 hook 强制执行，不要只靠文字。** 已知事实：光在 prompt 里好好说，并不能可靠地阻止 agent 在界面明显坏掉时标记「通过」；有个自动游戏工厂的创作 agent 甚至不跑验证器，直接自报「通过」。验证必须是**阻断式**的，不能只是建议。把 `templates/hooks/check-relay.py` 复制到项目的 `.game-forge/` 下，并在项目的 `.claude/settings.json` 里注册 SessionStart 和 Stop 两个 hook（配置见脚本头部注释）。本会话改了代码时，它会在收工时检查：改动之后有没有重跑主线通关、HANDOFF 顶部有没有写主线状态。没做到就拦住，不让收工。

给老板一段话的总结：乐趣假设、MVP 要回答的问题、M0 和 M1 的验收标准。

## 抢救模式：已有代码但玩不通或不好玩

1. **先实际跑一遍。** 启动游戏，尽量用脚本走一遍，记录实际能玩到第几步、卡在哪。不看代码先下结论。
2. **和老板反推设计**：按 A1 拿到乐趣假设，按 A6 拿到 MVP 边界。已有代码只是素材，不是约束。
3. **冻结所有功能开发。** 写出主线通关路径和脚本，此时大概率是红的。
4. **砍**：不在主线上、也不服务于乐趣假设的功能，关掉或删掉。沉没成本不是保留理由。
5. 落盘 GAME.md / RELAY.md，进入接力开发，从「修到主线全绿」开始。
