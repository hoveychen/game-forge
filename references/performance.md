# 性能：开工就定下来的几件事

这一章讲**和引擎无关的原理**：帧时花在哪里、哪些决定必须在开工时做、怎么量。Godot 怎么落地见第五节，其他引擎按原则自己对应。两个项目的实测放在附录里当证据，它们是例子，不是规则。

`templates/CONVENTIONS.md` 的「性能」条目是本章的可执行摘要，执行会话只看得到那一条。改本章结论时，同步改那一条。

## 一、核心判断：性能问题多半是开工那天定下的

最贵的几类性能问题都来自开头的几个选择：

- 表面花纹是现算还是查表；
- 灯是实时算还是预烘；
- 画质分档从哪里判断；
- 主线程会不会停下来等 GPU；
- 大量同类对象由谁来更新。

这些选择在开头只是一行代码，等内容铺满再改，就要动整个项目。而它们的代价在开发机上几乎看不出来：开发机 GPU 每像素的着色能力是中端手机的几十倍。

所以性能目标必须写**发布的最弱设备**，不能写开发机。性能工具也要和迭代工具同一天建。

## 二、帧时花在哪里：一个够用的成本模型

1. **GPU 时间 ≈ 像素数 × 每像素成本 + 固定部分。**
   - 像素数的乘数：屏幕分辨率 × 设备像素比、渲染比例、MSAA 倍数、同一像素被画几遍。
   - 每像素成本：着色器的运算量、它占的寄存器（占得越多，GPU 能同时跑的像素越少）、取样和读写的带宽。
2. **手机 GPU 和桌面 GPU 的瓶颈不一样。** 手机多是分块渲染（tile-based）。这类 GPU 上，片元着色的运算、寄存器占用、把多重采样或深度结果写回内存的带宽，往往比三角形数量和重叠绘制更贵。所以在桌面上有效的「减面、减重叠」在手机上常常不省；而「把某个每像素运算整个拿掉」才省。
3. **CPU 主线程时间 = 脚本/逻辑 + 提交绘制 + 等待。** 等待包括同步读回 GPU 数据、第一次用到某个着色器变体时现编、在主线程上解码资源。等待在 profiler 里常常不显示为「热函数」，要单独看。
4. **单项成本不能相加。** 显示器按刷新率把帧时截成几档（120 Hz 屏上是 8.3 / 16.7 / 25 / 33.3 ms），某项改动省下来的毫秒，取决于它让帧跨没跨档。

## 三、开工就定的原则

下面每一条都是「开头一句话，事后一个项目」的决定。第五节给出各引擎怎么做。

| # | 原则 | 背后的成本 |
|---|---|---|
| 1 | **画质分档只有一个入口**，按设备类别判断（手机、平板、桌面，包括手机上的浏览器），所有降级都读这个档位：分辨率、MSAA、阴影、密度、人数上限 | 分档按「哪个平台的包」来判断，网页包里的手机就漏掉了 |
| 2 | **不在着色器里每像素现算不随时间变的东西。** 多八度噪声、维诺纹理、程序花纹离线烘成可平铺贴图，运行时取一次样 | 每像素运算 × 满屏像素；手机上一张满屏地面就能吃掉十几 ms |
| 3 | **不靠成堆的实时灯。** 多盏小灯烘成光照贴图、光池或体素；风格化场景里，主光可以在着色器里自己算 | 灯越多，片元着色器越长、寄存器越多 |
| 4 | **像素数的乘数要封顶。** 设备像素比封顶（约 1.5–2），3D 渲染比例和 MSAA 跟着画质档走；MSAA 解析只解要用的缓冲（通常只要颜色） | 高 dpr 手机的像素数是 1× 的 4–7 倍 |
| 5 | **主线程不同步等 GPU。** 不在运行时读回网格、贴图、帧缓冲；需要的数据在生成时自己留一份，必须读回的用异步接口 | 网页和手机上每次读回都会把 GPU 管线排空 |
| 6 | **着色器变体在加载时编完。** 加载页把每种材质 × 灯光 / 阴影组合各画一帧；开关灯用改强度，不用增删灯或隐藏灯，免得生成新变体 | 网页上第一次用到一个变体要现编，一次就超过 1 秒 |
| 7 | **大量同类对象由一个管理器统一更新**，按 10–20 Hz 节流，屏外的停掉。不要每个对象各挂一个每帧回调；也不要每帧改材质参数，频繁变的状态写进一张共用贴图或实例数据 | 手机上的脚本开销是开发机的 5–7 倍；帧率越低，按次数算的开销越重 |
| 8 | **被盖住的不画。** 全屏不透明界面打开时停画 3D；离屏渲染目标按实际物理像素开 | 白画一整个世界 |
| 9 | **一次性的重活不放在玩家操作那一帧。** 加载脚本、解码图片、生成网格、排版，挪到加载页、空闲帧，或者分到几帧里做 | 第一次点按钮那一帧卡几百 ms |
| 10 | **音频不依赖主线程准时。** 用平台原生或独立线程的播放方式；总线和效果在配置里静态声明 | 主线程一卡，流式混音就断音 |
| 11 | **运行时不生成几何体**（约定「资产走离线管线」那条已经覆盖） | 生成本身慢，还常常伴随读回 |

## 四、量：方法比手段更能迁移

### 工具，和迭代工具同一天建

1. **游戏内性能面板。** 网页用 URL 参数（比如 `?perf=1`）打开，原生包用快捷键。面板上要有：
   - 设备行：显卡名、真实设备像素比、画布像素、渲染比例；
   - 帧时：中位数加一个**分位数**，比如 p60 = 帧时 ≤16.7 ms 的帧占的比例；
   - 计数：draw call、图元、着色器现编次数；
   - 一排开关，每个开关拿掉一大块：藏人、藏建筑、藏界面、关 MSAA、关阴影、渲染比例 50% / 70%；
   - 一个**自动对照**：在性能基准场景里（停游戏时钟、冻住动画、镜头复位、关自动降档）把每个开关按 A/B/A 轮流量几秒，每一档前后各夹一次基线，出一张表。

   **性能基准场景**单独建，不拿整局游戏代替：按 GDD 最重的几种画面各搭一个，随机种子、对象数、特效量写死，镜头走录好的轨迹，一条命令跑完出 JSON。整局游戏每次的负载都不一样，两版各跑一局的差别分不清来自改动还是来自这一局；节奏 bot 多半无头快进，连渲染都没在跑。约定里「按问题选测量台」那条是这一段的摘要。

   老板用手机打开截一张图，就是一次真机测量。
2. **函数级 profiler**：能在 release 包里按函数的 self 时间排名。长帧要分出主线程 CPU 时间和等待时间。
3. **优化先做成开关**，在同一进程里自证：开关关回去要像素零差，然后拿真机数字决定要不要设成默认。

### 方法

1. **先出排行再动手。** 没点名最贵的那一块就去加缓存、加跳过、加分帧，属于打补丁。
2. **用不受负载影响的量来归因**：函数 self 时间、主线程 CPU 时间、计数器。墙钟在共享机器上会抖 ±40%，只能做最终验收。
3. **高刷屏看分位数，不看中位数**（理由见第二节第 4 条）。
4. **开发机推断要等真机确认。** 开发机和手机的差距不是一个固定倍数：着色、脚本、驱动开销各差各的；同一个开关在两边甚至可能方向相反。
5. **GPU 计时查询**（WebGL 的 `EXT_disjoint_timer_query` 之类）只看方向，绝对值常常虚高好几倍。

### 量过常常不省的（先确认瓶颈再做）

- 减三角、减面、减重叠绘制、关深度预渲染：瓶颈在片元着色时，几乎不省。
- 把 uniform 折成常量、剪掉几条指令：寄存器占用不变就不省。
- 关 MSAA 改后处理抗锯齿：后处理本身也是一个满屏 pass，常常不省，画面还会糊。
- 合批减 draw call：计数降得很好看，但只有在 CPU 提交是瓶颈时才省。

## 五、Godot 4 怎么落地（实测）

下面每一条都在 yellow 或 human-zoo 里实测过。其他引擎还没有项目实测过，等有了对应的项目再补；在那之前，按第三节的原则自己查当前版本的文档。

| 原则 | Godot 4 的做法 |
|---|---|
| 1 分档入口 | 一个 Settings 单例；网页手机用 `OS.has_feature("web_android")` / `"web_ios"`，原生手机用 `"mobile"` |
| 2 噪声烘贴图 | 离线生成平铺 PNG，全局 sampler 取样 |
| 3 少实时灯 | 多盏灯烘成光池或体素贴图，主光在 toon 着色器里手算 |
| 4 像素乘数 | 网页模板里封顶 `devicePixelRatio`；`scaling_3d_scale`、`msaa_3d` 跟着档位走；导出后把 `index.js` 里 `blitFramebuffer` 的掩码改成只解颜色 |
| 5 不同步读回 | 别用 `surface_get_arrays`、`get_image`，生成网格时自己留数据 |
| 6 变体预编 | 加载页每种组合画一帧；关灯用能量 0，不用 `visible=false` |
| 7 同类对象统一更新 | 管理器按 Hz 更新，屏外停；状态写共用贴图，不每帧 `set_shader_parameter` |
| 8 盖住不画 | 全屏界面时关掉 3D 视口的渲染 |
| 10 音频 | 总线写进 `default_bus_layout.tres`，不在运行时 `add_bus`；网页用采样播放（`default_playback_type.web=1`） |
| 工具 | Tracy 版 release 导出模板 + 游戏内面板 |

## 六、规划阶段怎么用

- 第 7 步落盘时，约定里的「性能」条目已经写成引擎中立的原则句，最后一句「Godot 里的对应做法」单独放 Godot 的写法。老板换了引擎，就把这一句整句换成新引擎的做法（按第三节的原则，查当前版本的文档）。原则句不动，`conventions.py check` 会逐字核对它们。
- 老板点名的性能目标（「手机网页 60 帧」「Steam Deck 满帧」）照原话写进性能条目，替换掉默认目标。
- GDD 的视觉清单里出现「很多灯」「程序纹理」「大片地表花纹」「大量人群」时，在资产管线一节写清楚它们怎么烘：光池贴图、平铺噪声图、人群实例化和 LOD。这是美术方案，不是流程。

## 附录：两个项目的实测（证据）

**yellow（爆款短剧社，Godot 4，3D 三渲二经营，网页包跑在 gl_compatibility 上）**

手机网页高画质从每帧 31 ms 磨到 16.7 ms，用了一周、几十个会话。终态是华为 Maleoon 920 上日景、夜景都 60 帧，p60 分别为 89% 和 92%。

真机上决定性的三项，对应原则 2、3、4：

| 改动 | 真机收益 |
|---|---|
| 着色器里 4 个八度的 fbm 换成预烘贴图 | 帧时中位数 −14.9 ms |
| 夜景里成堆的点光烘成体素光池 | 夜景 29.8 → 16.8 ms |
| MSAA 只解颜色 | −14.5 ms |

其余有效的改动：

- 网页上屏时不再同步查询 GL 状态：M4 上渲染段 1.7–2.3 → 0.6–0.9 ms（原则 5）；
- 预热补洞：开机后现编 95 → 15 次（原则 6）；
- 姿势降频加屏外停：脚本时间 −43%（原则 7）；
- 全屏界面停画 3D：DC 533 → 290（原则 8）；
- 音频改采样播放：主线程卡 2 秒时断音 1829 → 0 ms（原则 10）。

量过不省的：

- 重叠绘制压掉近 4 层，真机只省 2.9 ms；
- 家具三角减半，GPU 0 差；
- uniform 折常量后指令减半，但寄存器占用不变，真机不省；
- 合批让 DC 普遍降了 10–50%，开发机 GPU 却测不出差别。

**human-zoo（开罗式经营，Godot 4，用 game-forge 流程做出来）**

约定里的性能目标只写了「Apple Silicon Mac 1080p 60fps」，执行会话就只在 Mac 上量过。原生手机档做得不错，但违反了：

- 原则 1：分档只认原生手机标签，手机浏览器跑的是桌面高画质（4× MSAA、太阳投影、读屏幕纹理的折射玻璃）；
- 原则 2：满屏的地面着色器每像素要算四次以上 fbm、两轮维诺，还整片带 `discard`；
- 原则 4：网页 dpr 没有封顶；
- 原则 10：运行时 `add_bus`。

它也没有任何性能工具，结论全靠墙钟。完整盘点在作者本机 Fleet wiki 的 `yellow/performance/week-retro-vs-humanzoo`。
